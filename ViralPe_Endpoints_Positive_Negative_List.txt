EPIC 1: USER ONBOARDING & AUTHENTICATION
--------------------------------------------------------------------------------

Story 1.1: Google Sign-In
• Endpoint: POST /api/auth/sign-in/google
  Description: Authenticates users using a Google OAuth2 ID Token.
  [+] Positive Test Cases:
      - Valid Google ID Token -> 200 OK. Returns { userId, token, profileComplete, message }.
      - Returning user with completed profile -> 200 OK with profileComplete: true.
  [-] Negative Test Cases:
      - Missing or empty idToken -> 400 Bad Request ("Google sign-in failed: ID token is missing.").
      - Invalid/Expired Google ID Token -> 400 Bad Request ("Google sign-in failed. Please try again.").
      - Google email unverified -> 400 Bad Request ("Google sign-in failed. Google email is not verified.").

Story 1.2: Apple ID Sign-In
• Endpoint: POST /api/auth/sign-in/apple
  Description: Authenticates users using Apple ID credentials (OAuth/Relay).
  [+] Positive Test Cases:
      - Valid Apple providerId, email, fullName -> 200 OK. Returns { userId, token, profileComplete }.
      - Returning user -> 200 OK with profileComplete: true.
  [-] Negative Test Cases:
      - Missing providerId or email -> 400 Bad Request ("Provider ID and email are required for sign-in.").
      - Empty request body -> 400 Bad Request.

Story 1.3: Mandatory Profile Completion — Pincode Entry
• Endpoint: GET /api/user/pincodes
  Description: Retrieves the master active postal directory.
  [+] Positive Test Cases:
      - Request active pincodes -> 200 OK. Returns array of [{ pincode, city, district, state, active }].
  [-] Negative Test Cases:
      - None (Public directory lookup).

• Endpoint: POST /api/user/validate-pincode
  Description: Validates a 6-digit residential pincode against the master postal directory.
  [+] Positive Test Cases:
      - Valid active pincode (e.g. "560001") -> 200 OK. Returns { pincode, city: "Bengaluru", district: "Bengaluru Urban", state: "Karnataka", valid: true }.
  [-] Negative Test Cases:
      - Non 6-digit pincode (e.g. "5600") -> 400 Bad Request ("Pincode must be a 6-digit value.").
      - Non-numeric input (e.g. "ABC123") -> 400 Bad Request ("Pincode must be a 6-digit value.").
      - Inactive/Unsupported pincode (e.g. "999999") -> 400 Bad Request ("Provided pincode is not supported.").

• Endpoint: POST /api/user/complete-profile
  Description: Submits residential pincode & locks profile permanently.
  [+] Positive Test Cases:
      - Valid payload { userId: 1, pincode: "560001", locationConfirmed: true } -> 200 OK. Profile marked immutable.
  [-] Negative Test Cases:
      - locationConfirmed = false -> 400 Bad Request ("Please confirm the pincode location before completing your profile.").
      - Submitting profile for an already completed user -> 400 Bad Request ("Profile is already completed.").
      - Non-existent userId -> 400 Bad Request ("User not found.").

Story 1.4: Mandatory Profile Completion — Referral / Onboarding Code
• Endpoint: POST /api/user/complete-profile (with optional referralCode)
  Description: Links user to referrer or vendor onboarder via code.
  [+] Positive Test Cases:
      - Valid referral code "REF101" -> 200 OK. Sets referred_by_user_id on user record.
      - Valid vendor onboarding code "VEND202" -> 200 OK. Sets onboarded_by_user_id on user record.
      - Empty referral code -> 200 OK (Code is optional).
  [-] Negative Test Cases:
      - Invalid referral code (e.g. "INVALID999") -> 200 OK with warning message ("Invalid referral code provided; profile completed without referral link."). User onboarding is not blocked.

Story 1.5: Block Access Until Profile Complete
• Endpoint: GET /api/user/profile?userId={id}
  Description: Retrieves profile details and checks profile completion status.
  [+] Positive Test Cases:
      - User with profileComplete: true -> 200 OK. Returns full user profile object.
  [-] Negative Test Cases:
      - Navigation attempt by user with profileComplete: false -> 403 Forbidden ("Profile incomplete. Pincode entry required.").
      - Missing userId query param -> 400 Bad Request ("User ID is required.").

EPIC 2: MULTI-LEDGER WALLET ARCHITECTURE
--------------------------------------------------------------------------------

Story 2.1: Wallet Dashboard Display
• Endpoint: GET /api/wallet/summary/{userId}
  Description: Fetches liquid Wallet Balance, Reversal Balance, 4 tracking ledgers, and Total Earnings sum.
  [+] Positive Test Cases:
      - Valid userId -> 200 OK. Returns { userId, spendableBalance, reversalBalance, cashbackLedger, referralLedger, vendorRoyaltyLedger, pincodeRoyaltyLedger, totalEarningsLedger }.
        Verification: totalEarningsLedger == sum(cashback + referral + vendor + pincode).
  [-] Negative Test Cases:
      - Invalid/Null userId -> 400 Bad Request ("User ID is required.").

Story 2.2: Wallet Balance Management
• Endpoint: GET /api/wallet/balance/{userId}
  Description: Retrieves current spendable liquid Wallet Balance.
  [+] Positive Test Cases:
      - Valid userId -> 200 OK. Returns { userId, balance }.
  [-] Negative Test Cases:
      - Non-existent userId -> Auto-initializes ₹0.0 balance (200 OK).

• Endpoint: POST /api/wallet/credit
  Description: Credits funds to liquid Wallet Balance.
  [+] Positive Test Cases:
      - Valid payload { userId: 1, amount: 500.0, category: "CASHBACK", sourceReference: "TX-101" } -> 200 OK. Wallet balance increases by ₹500.0.
  [-] Negative Test Cases:
      - Negative amount (e.g. -100.0) -> 400 Bad Request ("Credit amount must be positive.").
      - Null category -> 400 Bad Request ("Category is required.").

• Endpoint: POST /api/wallet/debit
  Description: Debits funds from liquid Wallet Balance.
  [+] Positive Test Cases:
      - Valid payload { userId: 1, amount: 200.0, category: "CHECKOUT", sourceReference: "CHK-102" } -> 200 OK.
  [-] Negative Test Cases:
      - Debit amount > spendable wallet balance -> 400 Bad Request ("Insufficient wallet balance.").
      - Debit amount <= 0 -> 400 Bad Request ("Debit amount must be positive.").

Story 2.3: Reversal Wallet — Instant Credit on Failed Transaction
• Endpoint: GET /api/wallet/reversal/{userId}
  Description: Retrieves Reversal Wallet balance with same-day expiration indicator.
  [+] Positive Test Cases:
      - Valid userId -> 200 OK. Returns { userId, balance, expiresAt: "23:59:59 Today" }.
  [-] Negative Test Cases:
      - Invalid userId -> 400 Bad Request.

• Endpoint: POST /api/wallet/credit-reversal
  Description: Instantly credits failed transaction amount to Reversal Wallet.
  [+] Positive Test Cases:
      - Post-payment gateway failure -> 200 OK. Reversal Wallet credited instantly with exact failed amount.
  [-] Negative Test Cases:
      - Invalid transaction reference -> 400 Bad Request.

Story 2.4: Reversal Wallet — End-of-Day Automated Sweep
• Endpoint: POST /api/wallet/sweep-reversal (Triggered automatically by @Scheduled cron at 00:00:00)
  Description: Sweeps non-zero Reversal Wallet balances via Refund-to-Source API & resets to ₹0.
  [+] Positive Test Cases:
      - Midnight sweep execution -> 200 OK. Sweeps all unclaimed reversal balances, initiates refund to original payment source, resets Reversal Wallet to ₹0.
  [-] Negative Test Cases:
      - Execution when all balances are ₹0 -> 200 OK (0 records swept).
      - Third-party refund gateway failure -> Logs error, triggers admin alert, retries refund execution.

Story 2.5: Informational Ledgers — Read-Only Tracking
• Endpoint: GET /api/wallet/activity/{userId}
  Description: Consolidated audit log of all wallet credits/debits with running balances.
  [+] Positive Test Cases:
      - Valid userId -> 200 OK. Returns array of [{ id, category, amount, sourceReference, runningBalance, createdAt }].
  [-] Negative Test Cases:
      - Missing userId -> 400 Bad Request.

Story 3.2: Partial Wallet Usage at Checkout
